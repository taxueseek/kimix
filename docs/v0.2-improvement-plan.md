## 〇、设计哲学

三条原则贯穿所有改进，按重要性排序：

1. **不做过度多代理** — Cognition 研究明确反对共享决策轨迹的多代理。Kimix 的子代理保持「只读探索 + 上下文隔离 + 结构化摘要回传」，不搞 Agent Swarm。
2. **token 是钱** — 每个进入上下文窗口的 token 都要有信号。哈希去重、token 预算、分层压缩是硬经济。
3. **用户掌控一切** — 权限三态（strict/auto/yolo）、敏感路径 deny、用户反馈学习，都是把控制权交给用户。

## 二、从参考项目中可吸纳的能力

### 来源 1：LeanToken — token 预算 + 哈希去重

LeanToken 的核心创新是「显式 token 预算 + 内容哈希去重」。实测减少 20-37% 输入 token。它作为 MCP Server 可以直接配置使用，但 Kimix 可以原生吸纳两个关键设计：

| 设计 | LeanToken 做法 | Kimix 现状 | 吸纳方案 |
|------|---------------|-----------|---------|
| **token 预算** | 每个工具响应有显式 token 上限，大文件不能占满请求 | context_budget_prune 已有 -41.7% 剪枝，但无 per-tool 响应预算 | 给所有工具输出加统一 token 上限中间件（已有 task_output 截断，推广到 read_file/grep/bash） |
| **哈希去重** | `receipt_id` + `known_hashes` 机制，已发送内容不重复发 | 无 | 在 ContextManager 加 `sent_hashes: HashSet<u64>`，相同内容哈希的代码片段不重复注入上下文 |
| **outline 工具** | 不读整个文件，只看定义/签名/导入 | kimix-codebase-graph 已有 tree-sitter go-to-definitions/references | 已存在，但未暴露为 agent 可调用的工具。新增 `outline` 工具暴露 codebase-graph 能力 |
| **精确范围读取** | `read` 工具读一个符号或闭合行范围，不读整个文件 | read_file 有 offset+limit 但在全量读取后才截取 | v0.1.14 已加 metadata 检查拦截大文件，但小文件的精确范围读取仍未优化 |

**实施优先级**：哈希去重 > outline 工具暴露 > token 预算推广

### 来源 2：Ami — 决策轨迹 + 反馈学习

Ami 的上下文图记忆（实体 + 关系 + 决策 + 反馈 + 写作风格）是 Kimix 记忆系统的进化方向。Kimix 已有 BM25 + 三级召回 + markdown 持久化，但缺少：

| 设计 | Ami 做法 | Kimix 现状 | 吸纳方案 |
|------|---------|-----------|---------|
| **决策轨迹** | 记录用户过去如何处理类似问题，相似任务复用决策 | 无 | 在 kimix-agent-memory 新增 `decisions` 表，记录 task_signature → decision → outcome |
| **反馈学习** | 用户编辑输出 → 更新写作风格；驳回任务 → 未来降权 | 无 | 在 agent loop 的 tool 执行后，如果用户修改了 agent 的输出，记录 diff 到 memory |
| **Obsidian 兼容** | 记忆导出为 markdown 知识图谱，git 版本化 | 已有 markdown 持久化 | 已存在，可增强 wiki-link 互引 |

**实施优先级**：决策轨迹（最有价值，让 agent「记住」用户偏好）> 反馈学习 > 写作风格

### 来源 3：Ante — 权限三态 + catalog.json + 离线推理

Ante 是最接近 Kimix 的竞品（同为 Rust 终端 agent），但有几个 Kimix 缺少的设计：

| 设计 | Ante 做法 | Kimix 现状 | 吸纳方案 |
|------|---------|-----------|---------|
| **权限三态** | strict（默认，未知都问）/ auto（未知都放，危险才问）/ yolo（全放） | 有 --always-approve（等价 yolo）但无 strict/auto 中间态 | 新增 strict 模式：未匹配规则的写操作需要确认。Shift+Tab 切换 |
| **session grants** | 批准一次后自动生成前缀规则（如 `cargo test *`），子sumption 感知去重 | 无 | 在权限层加临时 allow 规则，会话结束清除 |
| **catalog.json** | 用户自定义 provider，支持 12+ 内置 + 自定义 | config.toml 的 `[model.xxx]` 已支持任意 OpenAI 兼容 API | 已存在等价能力，但用户体验不如 Ante 的分离式 catalog。可改善文档而非代码 |
| **离线 GGUF** | 内置 llama.cpp 推理引擎，`--offline-model` 指向 GGUF 文件 | 无 | 重资产方向，违背「不引入运行时依赖」原则。中期再议 |
| **gateway 模式** | `ante gateway` 作为 Slack/Discord bot 运行 | 无 | 场景不同，Kimix 定位终端工具，不吸纳 |
| **status_line_command** | 用户自定义 shell 命令渲染状态栏 | 无 | 小而美的体验改进，~50 行实现 |
| **auto_compact** | 接近上下文限制时自动摘要 | context_budget_prune 已有，但不是 auto-compact 语义 | 增强：当 token 使用超 80% 时自动触发 compaction 摘要 |
| **short_prompt** | 精简系统提示 + 更短工具描述 | 无 | 可作为 `--short-prompt` CLI 选项，省 ~2K tokens/turn |

**实施优先级**：权限三态 > auto_compact > session grants > status_line > short_prompt

### 来源 4：Kigi-CLI 差异 — 4 个缺失 crate

| crate | 功能 | 行数 | 吸纳价值 |
|-------|------|------|---------|
| interjection-core | 用户中途插话（mid-turn interjection） | 320 | 高：用户在 agent 执行中发消息不被忽略 |
| tracing-macros | `timed!` 宏测量代码块执行时间 | 214 | 中：性能可观测性标准化 |
| markdown-core | 无头 Markdown 分析（不拉 TUI 渲染栈） | 1070 | 中：headless 模式轻量化 |
| secrets（URL 参数脱敏增量） | SENSITIVE_QUERY_PARAMS | ~30 | 低：补全 URL query 参数脱敏 |

## 七、关键设计决策记录

### D1：为什么不做 Agent Swarm

Cognition AI 的研究《Don't Build Multi-Agents》明确指出：多代理不共享决策轨迹导致行动冲突。Kimix 的子代理体系（Explore/Plan/GeneralPurpose）已经覆盖了「上下文隔离 + 只读探索」的核心需求。Agent Swarm 的 300 并行子代理在终端场景没有收益，只有复杂度。

### D2：为什么吸纳 Ante 的权限三态而不是 Claude Code 的 deny-first

Claude Code 的 deny-first 太重，终端用户需要更灵活的控制。Ante 的三态模型（strict/auto/yolo）+ session grants 是更好的折中：strict 默认安全，auto 日常高效，yolo 无人值守。Shift+Tab 实时切换。

### D3：为什么吸纳 LeanToken 的哈希去重而不是直接集成 LeanToken

LeanToken 作为 MCP Server 可以直接配置使用（文档化即可），但哈希去重是 ContextManager 层面的能力，应该在 Kimix 原生实现。原因：MCP Server 的工具调用经过 JSON-RPC 序列化，而原生实现可以共享内存中的哈希集合，零序列化开销。

### D4：为什么吸纳 Ami 的决策轨迹而不是完整上下文图

Ami 的完整上下文图（实体 + 关系 + 决策 + 反馈 + 写作风格）是 5 个维度，但决策轨迹的 ROI 最高：它让 agent「记住」用户过去如何处理类似问题，直接提升任务成功率。其他维度（写作风格、反馈学习）需要大量交互数据才有价值，中期再做。
